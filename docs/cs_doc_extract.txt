引言
目的和范围
本文档用于说明“基于 C/S 架构的 A 股模拟证券交易系统”的总体设计、功能边界、核心流程、数据库结构以及性能与安全实现方式，为后续系统开发、测试、演示和维护提供统一依据。系统以课程实验要求的迷你证券交易系统为基础，将原有操作员录入式柜台系统扩展为安卓用户端、柜台操作员端和交易后台服务端协同运行的 C/S 架构系统。
本系统的业务范围限定为 A 股现货模拟交易，支持开户注册、客户审核、账户生成、行情查询、买入卖出委托、撤单、成交回报、税费计算、资产持仓更新、风控预警和查询报表。系统不接入真实交易所，也不处理真实资金划转，而是通过模拟报盘与成交回报引擎复现证券公司柜台侧交易链路，以保证实验系统的合法性、可实现性和演示完整性。
背景
实验指导书要求设计一套迷你证券交易系统，系统需支持客户开户、委托下单、撤单、成交录入和客户信息查询等基本业务，并要求使用附件公共数据完成字典、证券、行情、佣金等辅助信息导入。基础要求虽然能够形成最小业务闭环，但对于追求较高完成度的项目而言，仅由操作员手工录入客户和委托信息，难以体现真实交易系统的多端协作、风险控制和工程化设计。
因此，本设计在基础要求之上引入安卓用户系统。安卓用户端用于产生真实的用户业务数据，包括开户申请、行情浏览、资产查询、委托提交和撤单申请；柜台操作员端负责开户审核、客户管理、代客下单、风控处理和成交回报；交易后台服务端统一承担认证鉴权、账户管理、交易风控、报盘处理、成交清算、税费计算和审计留痕。通过该设计，系统既满足课程实验的演示要求，又能体现接近实际证券业务系统的分层架构和处理逻辑。
术语和定义
C/S架构
客户端与服务端分离的系统架构。本系统中安卓用户端与柜台操作员端均为客户端，交易后台服务端承担核心业务处理。
安卓用户端
面向普通投资者的移动端系统，用于提交开户申请、查看行情与资产、发起委托和撤单。
柜台操作员端
面向证券公司操作人员的客户端，用于审核开户、维护客户、处理风控事件、录入成交回报和查询报表。
模拟报盘
系统将内部委托转换为报盘请求，并由模拟交易所环境返回受理、成交或撤单结果的过程。
成交回报
模拟报盘引擎返回的成交信息，作为系统生成成交单、计算费用和更新资产的依据。
资产流水
记录资金或证券资产发生变化的流水账，用于追踪冻结、扣减、释放、成交和费用扣收过程。
幂等控制
通过客户端请求流水号和服务端唯一约束，保证重复提交不会生成重复业务单据。

设计概述
系统架构
系统采用 C/S 架构，由安卓用户端、柜台操作员端、接入层/API 网关、交易后台服务层、模拟报盘与成交回报引擎、数据与基础设施层组成。安卓用户端与柜台操作员端不直接访问数据库，所有业务请求均经 API 网关进入后台服务。后台服务以账户、交易、风控、报盘和清算为核心，统一完成数据校验、交易规则判断、资产变动和日志审计。
图2-1 基于 C/S 架构的 A 股模拟证券交易系统架构图
从职责上看，安卓用户端负责将真实用户行为转化为标准化业务请求，柜台操作员端负责对需要人工判断的业务进行审核和处置，后台服务端负责保持业务状态和资产数据的一致性。模拟报盘与成交回报引擎不承担真实撮合职能，而是作为课程项目中的模拟交易所环境，用于生成受理、废单、部分成交、全部成交和撤单回报。

主要状态变化
本系统将业务状态管理作为核心设计内容。开户申请、委托、报盘、撤单和成交均采用状态驱动方式处理，任何状态变化都需要对应业务原因和流水记录，避免出现资产已变更但单据状态未更新，或者委托已撤销但冻结资金未释放的异常情况。

公共算法
公共算法主要用于账户生成、交易校验、税费试算、成交实算和资产更新。系统将佣金、印花税等费率从规则表读取，避免将费用规则硬编码在程序中。对于安卓端提交的委托，服务端会先依据行情、账户和持仓数据进行试算，确认资金或股份可用后再生成正式委托。
买入冻结金额
冻结金额 = 委托价格 × 委托数量 + 预估佣金 + 预估税费
卖出冻结数量
冻结数量 = 委托数量
成交金额
成交金额 = 成交价格 × 成交数量
佣金
佣金 = 成交金额 × 佣金费率，费率来源于佣金规则表
印花税
印花税 = 成交金额 × 印花税率，通常仅卖出方向收取
成交净额
买入净支出 = 成交金额 + 费用；卖出净收入 = 成交金额 - 费用
剩余冻结释放
释放金额或数量 = 原冻结值 - 已成交占用值 - 待撤占用值
功能及处理流程
系统功能以“用户端产生业务请求、柜台端完成审核处置、后台服务保证状态和资产一致”为主线组织。为了兼顾实验要求和扩展设计，系统保留操作员代客录入能力，同时将安卓用户端作为主要数据来源，使开户、委托、撤单和成交记录能够形成更接近真实业务的闭环。
图3-1 核心业务闭环流程图
安卓用户端
安卓用户端面向普通投资者，主要承担用户注册登录、开户注册、行情查看、资产查询、委托提交、撤单申请和通知接收。用户在注册登录后，可以提交开户申请，系统会保存其实名信息、证件信息、资产账户类别和沪深证券账户信息。开户申请未通过前，用户只能查看基础行情和申请进度；审核通过后，用户与正式客户代码、资金账户和股东账户完成绑定，方可进行委托交易。
用户下单时，客户端只负责采集证券代码、买卖方向、委托价格和委托数量，所有交易规则均由服务端校验。服务端返回受理结果后，安卓端通过订单查询或通知中心查看委托状态、成交结果、撤单结果和风控提示。为避免重复点击造成重复下单，客户端每次提交委托时生成唯一请求流水号，服务端通过幂等约束保证同一请求只处理一次。
柜台操作员端
柜台操作员端面向证券公司内部人员，负责处理需要人工判断或管理权限的业务。操作员可以审核用户端提交的开户申请，也可以按照实验要求直接录入客户资料并完成开户；可以查询客户资料、资产持仓、委托和成交记录；可以在特殊情况下进行代客下单、成交回报录入、风控事件处理和基础数据维护。
柜台端的设计重点不是替代用户端，而是作为业务审核和运营管理入口。所有操作员行为均写入操作日志，敏感操作如开户审核、风控解除、成交回报录入和基础费率维护需要记录操作时间、操作对象、处理前后状态和处理说明，以便后续追溯。
开户与账户管理
开户流程从用户端或柜台端发起。用户端发起时，系统先生成开户申请单并进入待审核状态；柜台端发起时，可以直接录入或批量导入客户资料，但同样需要通过字段完整性、证件唯一性、股东账户规则和资产账户类别校验。审核通过后，后台生成正式客户代码，并自动开设资金账户和沪深股东账户，再根据客户模板初始化资金和持仓。

委托下单
委托下单支持买入和卖出两类业务。安卓用户端和柜台操作员端均可提交委托，但后台处理逻辑保持一致。系统接收委托后先进行身份和权限校验，再校验证券代码、市场、交易方向、价格、数量和行情限制。对于买入委托，后台计算预估所需金额并冻结资金；对于卖出委托，后台检查可卖持仓并冻结股份。冻结成功后，系统生成正式委托单，并通过报盘服务生成报盘流水。
委托单生成后，系统不会立即视为成交，而是进入模拟报盘流程。报盘引擎返回受理结果后，委托状态更新为已报或废单；若返回成交回报，则根据成交数量推进为部分成交或全部成交。该设计使系统能够完整体现交易业务中的委托、报盘、回报、成交与清算分离。
委托撤销
撤单流程用于处理用户或操作员对未完全成交委托的撤销请求。系统只允许对已报、部分成交且仍有未成交数量的委托发起撤单。撤单申请生成后，报盘服务向模拟报盘引擎提交撤单请求；当撤单成功回报返回时，后台释放未成交部分占用的冻结资金或冻结股份，并将原委托更新为已撤或部撤。
为了防止重复撤单，撤单申请同样采用请求流水号和撤单单号控制。若同一委托已经处于撤单申请中、已撤或已成状态，系统将拒绝新的撤单申请，并生成明确的业务错误提示。
成交回报与清算
成交回报既可以由模拟报盘引擎自动生成，也可以由柜台操作员按照实验演示要求手工录入。后台收到成交回报后，先校验成交单号是否已处理，避免重复清算；随后生成成交记录，计算成交金额、佣金、印花税和其他费用，并更新委托的累计成交数量、累计成交金额和平均成交价格。
清算处理是资产一致性的核心。买入成交时，系统将冻结资金转为实际扣减，并增加对应证券持仓；若预冻结资金大于实际成交支出，则释放差额。卖出成交时，系统扣减冻结股份，增加资金余额并扣除税费。每一次资金或股份变化均写入资产流水，使账户余额、持仓数量、委托状态和成交记录能够相互校验。
风控处理
风控系统分为交易前风控、交易中监控和交易后审计。交易前风控主要用于拦截非法委托，例如客户未开户、账户冻结、资金不足、持仓不足、价格超出涨跌停、证券代码不存在、委托数量不符合交易单位等。交易中监控主要记录大额委托、高频撤单、异常设备登录和短时间重复请求等事件。交易后审计主要面向操作员敏感操作、资产异常变动和成交清算结果。
风控类型
主要规则
处理方式
身份与权限风控
用户是否登录、是否开户、账户是否正常、操作员是否有权限。
不满足条件时直接拦截并记录风险事件。
交易规则风控
价格涨跌停、买入资金、卖出持仓、委托数量、单笔金额上限。
交易前同步校验，命中硬规则时拒绝下单。
行为风控
高频撤单、重复请求、异常设备、接口访问过快。
根据规则进行预警、限流或拦截。
清算审计
成交重复处理、资产变动异常、操作员敏感操作。
写入风险事件和操作日志，必要时由柜台端处理。
报表查询
报表查询面向用户端和柜台端提供不同粒度的数据展示。安卓用户端只允许查询本人客户信息、资金资产、持仓、委托、成交、通知和资产流水；柜台操作员端可按客户代码、资金账户、证券账户、委托编号、成交编号和日期区间查询业务数据。系统通过统一查询服务封装数据库访问，避免客户端直接拼接查询条件。

查询本人资金余额、可用资金、持仓数量和可卖数量。

风控日志
查看与本人相关的风险提示。

数据库概要设计
数据库分域
数据库沿用前期 27 张核心表的设计思路，并在 C/S 架构下补充用户接入域。整体上分为基础主数据域、用户接入域、开户账户域、交易报盘域、风控审计域五个部分。基础主数据域承接附件公共数据，用户接入域保存安卓端用户、设备、登录和通知信息，开户账户域维护客户、账户和持仓，交易报盘域记录委托、撤单、报盘、成交和费用，风控审计域记录规则命中、操作日志和接口访问情况。

4.3表间关系说明
表间关系以客户和账户为中心展开。安卓用户通过开户申请转化为正式客户，正式客户下挂资金账户和沪深股东账户，资金账户下维护当前持仓。委托单关联客户、资金账户、股东账户和证券主数据，报盘流水、撤单申请、成交记录和费用明细均围绕委托单展开。资产流水以资金或证券资产变动为记录对象，关联委托、成交、撤单等业务来源，实现从前端请求到后台清算的全过程追踪。

性能、安全与部署设计
性能设计
系统性能设计围绕高频读、关键写和一致性控制展开。行情、字典、佣金、税费和证券主数据属于高频读取数据，适合放入 Redis 或本地缓存，减少每次下单和行情查询时的数据库访问。安卓端自选股行情采用批量查询接口，避免一个证券一次请求造成接口压力。
交易写入链路以数据库事务保证一致性。下单时委托记录、资金或持仓冻结、资产流水和报盘流水应在同一事务边界内完成；成交清算时成交记录、费用明细、资产更新、委托状态更新和流水记录也应保持一致。资金账户、当前持仓和委托表设置 version 字段，通过乐观锁或数据库行锁避免重复扣减和超卖问题。
安全与审计设计
安全设计以“客户端不可信、服务端统一校验”为原则。安卓端和柜台端均需登录后访问系统，服务端通过 Token 鉴权确认用户身份，并根据角色区分用户端与操作员端权限。用户只能访问本人客户资料、资产、持仓和委托；操作员访问客户数据时需记录查询和操作日志。
系统对敏感操作进行审计留痕，包括开户审核、客户资料修改、代客下单、风控事件处理、成交回报录入、基础数据维护和账户状态调整。接口访问日志记录请求路径、请求时间、来源 IP、耗时和返回状态，便于后续排查异常请求。对于重复下单、频繁撤单、异常设备登录等行为，系统写入风险事件并在柜台端展示。
部署与运行设计
系统部署采用轻量化方式实现。安卓用户端运行在移动设备或模拟器上，柜台操作员端可采用桌面客户端或管理端程序，二者均通过 HTTPS 调用交易后台 API。后台服务端部署为单体应用，但内部按照认证、开户、账户、行情、交易、报盘、风控、清算、通知和报表模块划分代码结构。MySQL 保存业务数据，Redis 用于缓存和简单限流，消息队列或异步任务用于通知推送、清算任务和日志异步写入。

测试与演示设计
测试设计围绕实验指导书要求的开户、委托、撤单、成交和查询业务展开，同时覆盖安卓用户端接入后的新增场景。正常路径应验证用户端提交开户申请、柜台端审核通过、后台生成客户代码和账户、用户端提交委托、报盘受理、成交清算和资产查询；异常路径应验证证件重复、账户未审核、资金不足、持仓不足、价格超限、重复下单、重复撤单和成交重复回报等情况。
